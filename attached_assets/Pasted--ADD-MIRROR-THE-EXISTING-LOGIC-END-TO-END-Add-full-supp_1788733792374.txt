# ADD סופי תיבות — MIRROR THE EXISTING ראשי תיבות LOGIC END-TO-END

Add full support for:

סופי תיבות

Use the SAME conceptual logic, matching behavior, saving behavior, badges, highlighting, and production-safety principles already used for ראשי תיבות.

IMPORTANT:
Do not bolt on an isolated calculation.
Treat סופי תיבות as a first-class derived value parallel to ראשי תיבות.

Before changing anything, inspect the current ראשי תיבות implementation and reuse its architecture wherever possible.

Do NOT redesign unrelated parts of the app.
Do NOT destructively migrate production data.

==================================================
1. DEFINITION
==================================================

ראשי תיבות:
first relevant Hebrew letter of each word.

סופי תיבות:
last relevant Hebrew letter of each word.

Example:

שקנו בג שח

ראשי תיבות:
שבש

סופי תיבות:
וגח

For סופי תיבות, take the final actual Hebrew letter of each word while ignoring trailing:

- punctuation
- spaces
- geresh / gershayim
- niqqud
- cantillation

Preserve the original displayed text.

==================================================
2. GEMATRIA
==================================================

Calculate:

1. the סופי תיבות string
2. גימטריית סופי תיבות

Reuse the EXISTING standard gematria engine.

Do not create a separate value system.

Final-form Hebrew letters must follow whatever normalization/value rules the existing standard gematria engine already uses.

Do not introduce special מנצפ״ך values unless the current app already defines them that way.

==================================================
3. MAIN CALCULATOR
==================================================

Add סופי תיבות without making the main result area feel crowded.

The user needs to be able to see:

- גימטריה מלאה
- ראשי תיבות
- גימטריית ראשי תיבות
- סופי תיבות
- גימטריית סופי תיבות

BUT do not simply create five oversized equal cards.

Use a clean hierarchy.

Preferred concept:

גימטריה מלאה
[main value]

ראשי תיבות
[letters] · [gematria]

סופי תיבות
[letters] · [gematria]

In other words, it is acceptable to combine each derived string with its gematria visually so the top calculation area remains simple.

Preserve the current premium RTL design.

==================================================
4. SAVE LOGIC
==================================================

When an entry is normally saved, derive and persist/index its סופי תיבות information in the same way that ראשי תיבות information is currently persisted/indexed.

Normal save should support:

- full gematria
- ראשי תיבות
- gematria of ראשי תיבות
- סופי תיבות
- gematria of סופי תיבות
- existing מילוי behavior according to the current rules

Do not require the user to separately click a "save סופי תיבות" action.

It is derived data.

==================================================
5. EXISTING ENTRIES
==================================================

Existing saved entries must also become searchable/matchable by סופי תיבות.

Do this safely.

Prefer an additive derived/indexing approach consistent with the current production architecture.

Do NOT:

- delete saved entries
- rewrite client text
- truncate tables
- reset production
- recreate the database
- copy development DB over production

If backfilling derived values is necessary, make it idempotent and production-safe.

Existing saved-entry text must remain unchanged.

==================================================
6. LIVE MATCHING — MIRROR ראשי תיבות
==================================================

Inspect exactly how ראשי תיבות currently participates in התאמות שמורות.

Implement the SAME categories for סופי תיבות.

Where ראשי תיבות supports:

- exact derived-letter match
- numeric gematria match
- saved-match reason metadata
- deduplication
- highlighting

סופי תיבות should support the equivalent behavior.

Do not invent a different matching philosophy.

==================================================
9. SIDEBAR HIGHLIGHTING
==================================================

This is important.

We just improved ראשי תיבות matches so the exact contributing letters inside the phrase are highlighted in the restrained gold accent.

Do the SAME for סופי תיבות.

For:

שקנו בג שח

סופי תיבות:

וגח

The phrase should remain:

שקנו בג שח

but highlight ONLY:

ו at the end of שקנו
ג at the end of בג
ח at the end of שח

Conceptually:

שקנ[ו] ב[ג] ש[ח]

DO NOT show brackets in the real UI.

Only the exact contributing letters should be gold.

==================================================
10. DIFFERENCE BETWEEN ראשי AND סופי HIGHLIGHTING
==================================================

ראשי תיבות match:

highlight contributing FIRST letters.

Example:

[ש]קנו [ב]ג [ש]ח

סופי תיבות match:

highlight contributing LAST letters.

Example:

שקנ[ו] ב[ג] ש[ח]

This must be visually precise.

==================================================
11. DO NOT HIGHLIGHT THE WRONG LETTERS
==================================================

Never:

- highlight every occurrence of the same letter
- highlight the whole word
- highlight the whole phrase
- simply search the rendered string for the characters

Map the derived letters back to the actual contributing words/characters.

Use existing match metadata and original text.

If mapping cannot be determined reliably, show plain text rather than an incorrect highlight.
