# #17 — Search Entire Tanach for Live Gematria Matches

## What & Why

Add a major discovery feature to the existing Gematria calculator:

As the user's CURRENT FULL GEMATRIA changes, automatically search the entire imported Tanach for contiguous Hebrew text whose standard gematria equals that current value.

The search should find:

1. **whole-word matches**
2. **whole multi-word phrase matches**
3. **partial-word / arbitrary contiguous-letter matches**

The user should see those Tanach discoveries directly underneath the main three-result Gematria panel.

The existing LEFT sidebar remains dedicated to the user's own:

**התאמות שמורות**

Do NOT mix the potentially large Tanach search result set into the personal saved-match sidebar.

Every Tanach result must allow:

- opening the exact location in תנ״ך;
- seeing the matching letters highlighted;
- saving the exact matched range into the existing personal saved library.

This should turn the workflow into:

**calculate → discover Tanach connection → inspect it → save it → it becomes part of the personal matching library**

---

# CORE DISTINCTION

There are now TWO different discovery systems.

## LEFT SIDEBAR — PERSONAL

**התאמות שמורות**

These are the user's personally saved calculations.

Keep the existing system and styling.

Do NOT replace it.

---

## UNDER CALCULATION — GLOBAL TANACH

Add a new section:

**התאמות בתנ״ך**

These are dynamically discovered occurrences anywhere in the imported Tanach.

This section belongs directly beneath the unified three-part result panel.

Do NOT render the full Tanach results in the left sidebar.

---

# PAGE ORDER

Calculator desktop flow should be:

1. input
2. unified three-result calculation panel
3. **התאמות בתנ״ך**
4. פירוט מילים

The left side continues to show:

**התאמות שמורות**

---

# WHAT VALUE DO WE SEARCH?

Tanach searching is driven by the CURRENT:

**full gematria**

of the calculator input.

Example:

Current:

`410 · תי`

Search the complete Tanach for every appropriate contiguous Hebrew range whose standard gematria equals:

`410`

Do NOT search Tanach separately for every auxiliary output in this phase.

ראשי תיבות matching remains part of the existing PERSONAL saved-match engine.

This new corpus search is specifically:

**current full gematria → matching contiguous Tanach text**

---

# EXACT SEARCH TYPES

Classify every Tanach match into one of three user-facing types.

## 1. WHOLE WORD

The selected range is exactly one complete Hebrew word.

Badge:

**מילה שלמה**

Example concept:

Current gematria = 410

A Tanach word with gematria 410 is discovered.

---

## 2. PHRASE / MULTIPLE COMPLETE WORDS

The selected range starts at the beginning of a word, ends at the end of a word, and spans TWO OR MORE complete consecutive words.

Badge:

**צירוף מילים**

Do NOT require the match to align to a verse boundary.

It may be any consecutive whole-word phrase inside one verse.

---

## 3. PARTIAL / CONTIGUOUS LETTER RANGE

The matching range starts and/or ends inside a word.

Badge:

**חלק ממילה**

The range may:

- be part of one word;
- start inside one word and continue through following words;
- end inside another word.

It must always be a CONTIGUOUS range of Hebrew text.

---

# IMPORTANT — CONTIGUOUS ONLY

Do NOT search for arbitrary non-contiguous combinations of letters.

Valid:

letters 10–18 of a verse

Invalid:

letter 2 + letter 19 + letter 47 simply because their values add to the target.

Only real contiguous Hebrew ranges count.

---

# VERSE BOUNDARY

For this phase, search ranges must stay within ONE פסוק.

Do NOT create matches that begin in one verse and continue into the next verse.

Cross-verse matching is OUT OF SCOPE.

---

# SEARCH ALGORITHM

Do NOT precompute every possible substring of Tanach.

That would produce unnecessary storage and complexity.

Standard Hebrew gematria values are strictly positive.

Therefore use an efficient sliding-window/two-pointer approach over the normalized Hebrew letters of each verse.

Conceptually:

- total < target → advance right
- total > target → advance left
- total === target → record match

This allows finding contiguous ranges in approximately linear time per verse/corpus scan.

The implementation must return ALL valid matches subject to pagination/display limits.

Overlapping valid ranges must not be incorrectly discarded.

---

# EXISTING TANACH REPRESENTATION

Reuse the existing Tanach infrastructure.

We already have:

- UXLC corpus

- grapheme/base-letter mapping
- word boundaries
- book/chapter/verse references
- cursor/range highlighting
- Tanach reader
- gematria calculation

Do NOT create a second unrelated Hebrew parser.

Extract/reuse shared range logic where appropriate.

---

# PERFORMANCE OPTIMIZATION

The basic calculator result must remain instant.

Tanach search runs separately.

Use approximately:

**300–350ms debounce**

after the latest relevant calculator change.

If another character is typed before the previous search completes:

- cancel it where practical;
- otherwise mark it stale;
- NEVER allow an older result to overwrite results for the newer gematria.

---

# CACHE BY GEMATRIA VALUE

Add server-side/in-memory caching where appropriate.

If gematria:

410

has already been searched recently, reuse the result rather than rescanning the entire Tanach unnecessarily.

Use a bounded cache strategy.

Do not introduce unbounded memory growth.

---

# QUICK WHOLE-WORD INDEX

Whole-word matches are common and should be very fast.

If useful, build or reuse a lightweight Tanach word-occurrence/index structure containing conceptually:

- normalized word
- gematria
- source verse
- word position
- start letter index
- end letter index

Index gematria appropriately.

Then:

whole-word searches can use an indexed lookup.

The arbitrary contiguous-range engine can handle phrase/partial matches.

Avoid returning the same exact range twice if both mechanisms discover it.

Deduplicate using a stable key such as:

book/division + chapter + verse + startLetter + endLetter

---

# DO NOT STORE EVERY POSSIBLE SUBSTRING

Explicitly avoid:

- one DB row per possible Tanach substring;
- an O(n²) corpus expansion;
- giant precomputed range tables.

That is unnecessary.

**הצג עוד**

# MATCH CLASSIFICATION RULES

## whole_word

## whole_phrase
