# MASTER IMPLEMENTATION — MULTIPLE מילוי VARIANTS, CLEAN UX

We need to generalize the existing multiple-מילוי functionality.

CURRENT PROBLEM:

The app currently exposes the special multiple-milui treatment mainly for:

יהוה

via the canonical מילויי הוי״ה area.

The client wants multiple valid מילוי spellings to be available ANYWHERE in the calculator when the current Hebrew word/phrase contains letters for which more than one accepted מילוי spelling exists.

However:

THE APP MUST REMAIN EXTREMELY SIMPLE.

Do NOT show every possible permutation.
Do NOT generate a giant table of combinations.
Do NOT turn מילוי into a configuration dashboard.

The UX principle is:

DEFAULT = one simple מילוי result.

ADVANCED VARIANTS = only appear when relevant.

USER CHOOSES one exact interpretation.

APP shows ONE live result.

USER may explicitly save THAT interpretation.

==================================================
1. PRODUCT MODEL
==================================================

There are now two different milui concepts:

A. DEFAULT / CURRENT מילוי

This is the normal calculation using the active default מילוי mapping.

It remains automatic.

It does NOT require a separate save.

--------------------------------------------------

B. EXPLICIT MULTI-VARIANT מילוי INTERPRETATION

If the current text contains a letter occurrence with multiple accepted spellings, the user may deliberately choose among those spellings.

That exact chosen combination is an interpretation.

The user may explicitly preserve it using:

שמור מילוי זה

This is NOT the same as normal:

שמור

and NOT the same as:

שמור כמילת יסוד

==================================================
2. THREE DISTINCT USER INTENTIONS
==================================================

Keep these concepts cleanly separate:

### שמור
Save the Hebrew phrase normally.

### שמור כמילת יסוד
Promote the complete phrase into the curated מילות יסוד collection.

### שמור מילוי זה
Preserve this exact user-selected מילוי interpretation.

Do not blur these concepts together.

==================================================
3. DO NOT SHOW MULTI-VARIANT UI UNLESS RELEVANT
==================================================

For a normal word where every letter currently has one accepted מילוי spelling:

show the normal מילוי UI only.

Do NOT show:

אפשרויות מילוי

Do NOT show disabled controls.

Do NOT show explanatory clutter.

--------------------------------------------------

If one or more letter occurrences have multiple accepted spellings:

show a small secondary trigger:

אפשרויות מילוי

Optionally include a subtle count such as:

אפשרויות מילוי · 2

where the count refers to the number of relevant ambiguous letter occurrences/types, whichever is clearest in the existing architecture.

Do not make the count visually important.

==================================================
4. THE TRIGGER MUST BE SUBORDINATE
==================================================

Inside the existing מילוי disclosure:

show the normal result first.

Then, only if variants exist:

אפשרויות מילוי

This should feel like an advanced disclosure.

It should NOT compete visually with the main מילוי result.

Use:
- small text
- subtle chevron
- restrained gold/navy interaction
- no giant card
- no large icon

==================================================

6. ONE RESULT AT A TIME
==================================================

Very important:

DO NOT calculate and display every possible combination as separate result cards.

If:

- ו has 3 possibilities

do NOT show 9 result cards.

Instead:

the user chooses one option for each relevant letter occurrence.

The result recalculates instantly.

There is ONE currently selected interpretation and ONE visible total.

This prevents combinatorial UI explosion.

13. REPEATED LETTER OCCURRENCES — IMPORTANT
==================================================

ה occurrence 2 → ה״י

This avoids locking the engine into an assumption that may later prove religiously/semantically incorrect.
